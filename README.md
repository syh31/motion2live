# motion2live

English | [简体中文](<README.zh-CN.md>)

Convert Android **Motion Photos** into **Live Photo image + video pairs** for import into Apple Photos.

Designed for the common “still image container + appended video” layout used by devices from
Samsung, Google, OPPO, and others. This does not mean every brand, model, or OS version has been
tested. This is a macOS command-line tool, with no graphical interface.

## Features and requirements

- Split JPEG (including Ultra HDR JPEG) and HEIC/HEIF Motion Photos.
- Locate appended MP4/MOV video using XMP length metadata or ISO-BMFF container scanning.
- Encode the still as HEIC or JPEG with ImageIO and write an Apple MakerNote pairing identifier.
- Attempt to convert HDR stills into images with ISO gain maps.
- Remux video with AVFoundation passthrough, without recompressing the video.
- Check image decoding and pairing metadata, report HDR information, and optionally test an
  actual import through the Photos API.

**The full pipeline requires macOS.** The image, video, and validation tools use Apple frameworks
such as ImageIO, AVFoundation, and Photos. They cannot run directly on Linux, Windows, or in a
standard Linux Docker container. The pure-Python splitter can run independently of these frameworks.

Build and runtime requirements:

- macOS 15 or later is recommended, with recent Xcode Command Line Tools / SDK that support the
  APIs used in the source. The code directly references newer HDR and AVFoundation APIs, with no
  compatibility branches for older systems. `--hdr sdr` does **not** make the project build or run
  on older macOS versions. The minimum working OS/SDK combination has not been systematically tested.
- Python 3.10+ is recommended. The scripts use only the standard library; no `pip install` is needed.
- The `swiftc` compiler. If Apple command-line tools are not installed, run `xcode-select --install`.

Compiled binaries and private test media are excluded from the repository; build the tools after
obtaining the source. Historical sample notes record successful pairing in Photos, but the project
does not have a comprehensive device/OS compatibility test matrix.

## Quick start

From the project root:

```bash
bash build.sh

python3 tools/motion2live.py /path/to/MOTION_PHOTO.jpg /path/to/output/IMG_LIVE \
  --hdr preserve
```

This produces two files with the same base name:

```text
IMG_LIVE.HEIC
IMG_LIVE.MOV
```

Import both files together into macOS Photos, preferably keeping the matching base names.
Pairing depends on identifiers inside the files: simply renaming two files to match does not create
a Live Photo. Confirm that the imported item is recognized as a Live Photo and plays correctly.
To transfer it to an iPhone, prefer sharing the recognized Live Photo from Photos. Sending the two
raw files directly via AirDrop is not guaranteed to pair them; behavior depends on the receiving
system and import method.

### HDR modes

```text
--hdr auto       Attempt HDR for sources detected as HDR; warn and attempt SDR fallback on failure (default)
--hdr preserve   For sources detected as HDR, require output headroom > 1.01 or fail
--hdr sdr        Use the SDR decoding and encoding path
```

`preserve` does not turn SDR input into HDR and does not guarantee lossless pixel or gain-map
preservation. Source HDR detection depends on the headroom or gain maps reported by ImageIO;
unrecognized HDR input may be treated as SDR. If HDR matters, use `--hdr preserve` and inspect both
the logs and the displayed result.

The default still format is HEIC. JPEG output uses the `.JPG` extension:

```bash
python3 tools/motion2live.py input.jpg IMG_LIVE --still-format jpeg --hdr preserve
```

### Conversion options

| Argument | Description |
|---|---|
| `src` | A single input Motion Photo file |
| `out` | Output base path; prefer a name without an extension or extra dots, such as `output/IMG_LIVE` |
| `--still-format heic\|jpeg` | Still image format; default: `heic` |
| `--hdr auto\|preserve\|sdr` | HDR policy; default: `auto` |
| `--uuid ID` | Custom pairing identifier; a random UUID is generated by default. Input is uppercased, but UUID syntax is not validated |
| `--date ISO8601` | Override the video date, e.g. `2026-09-11T02:45:51Z`; does not change the still image's EXIF date |
| `--primary N` | Explicit video start offset in bytes; it must still pass the MP4/QuickTime boundary check |
| `--video-length N` | Appended video length hint; not a video trimming option |
| `--force` | Allow replacement of existing output files |
| `--no-validate` | Skip the final structural and pairing check; the still encoder's own checks remain enabled |

Show help:

```bash
python3 tools/motion2live.py --help
python3 tools/make_livephoto_still.py --help
```

By default, conversion refuses to overwrite either output file. Processing takes place in a temporary
directory under the output directory, then the two destination files are replaced in sequence.
Publishing the pair is **not** a single atomic transaction. Do not use the source file as an output,
or run concurrent conversions to the same output base path. The tool processes one input at a time;
there is no built-in batch directory mode.

## How extraction works

The [splitter](<tools/make_livephoto_still.py>) follows this sequence:

1. Use `--primary` if an explicit offset is provided.
2. Otherwise, use `--video-length` or the video length from XMP `Container:Item` entries.
3. Also recognize `GCamera:MicroVideoOffset`, `GCamera:MotionPhotoVideoLength`, and `OpCamera:VideoLength`.
4. If length metadata is missing or the resulting boundary is invalid, scan for an appended
   ISO-BMFF `ftyp/moov/mdat` structure.
5. Copy all bytes before the video start into the still output, and all bytes from the video start
   to the end of the file into the video output.

Splitting does not decode or rewrite the still container, so MPF data, gain maps, and HEIF auxiliary
images within that prefix are preserved. It does not repair existing metadata or write a Live Photo
MakerNote into the still. XMP parsing handles common patterns implemented in the source, rather than
being a complete XML/XMP parser; malformed numeric values and similar issues may cause an error.

To split a file without building the Swift tools:

```bash
python3 tools/make_livephoto_still.py input.jpg /tmp/source.jpg \
  --video-out /tmp/source.mp4 \
  --id-file /tmp/content-id.txt
```

For HEIC input, use a `.heic` still output name. The splitter does not convert formats based on the
file extension. `--id-file` only saves the generated or supplied pairing identifier for later steps.

If automatic detection fails but you know a valid video boundary, specify it manually
(the offset below is only an example):

```bash
python3 tools/make_livephoto_still.py input.jpg /tmp/source.jpg \
  --video-out /tmp/source.mp4 \
  --primary 8184744
```

Even with `--video-length`, extraction ultimately extends to the end of the file; extracting an
arbitrary fixed-length segment is not supported. An explicit offset cannot make an unsupported
proprietary container into a supported MP4/MOV.

## HDR implementation and image quality

The [still encoder](<tools/mkstill.swift>) uses ImageIO to:

1. Detect HDR input from headroom or auxiliary gain-map information.
2. Decode extended dynamic range and request ISO gain-map encoding on the HDR path.
3. Write HEIC/JPEG output together with Apple MakerNote key 17.
4. Read the output back, check that it decodes and that the MakerNote matches, and report headroom.
5. Require output headroom greater than 1.01 when the source is detected as HDR and `preserve` is used.

This is re-encoding, not a byte-for-byte copy of the original gain-map bitstream or pixels.
**Both SDR and HDR stills are re-encoded.** Colors, brightness, and detail may differ from the source;
actual HDR presentation depends on the system, encoder, and viewing software.
Video uses passthrough, but the MOV container, metadata, and timestamp fields change, so the entire
video file is not byte-identical to the extracted source.

## Live Photo pairing implementation

The still image receives:

```text
kCGImagePropertyMakerAppleDictionary
key 17 = <ContentIdentifier UUID>
```

The MOV receives these file-level QuickTime metadata entries:

```text
com.apple.quicktime.content.identifier = <the same UUID>
com.apple.quicktime.still-image-time   = 0
com.apple.quicktime.live-photo.auto    = 1
```

An XMP `apple:ContentIdentifier` does not replace the pairing identifiers in the still's MakerNote
and the MOV. The current implementation writes these keys through `AVAssetExportSession.metadata`.
It **does not create a separate timed metadata track**, nor does it read the Android Motion Photo's
still-frame timestamp. This is not a complete reproduction of the native iPhone Live Photo structure;
compatibility must still be tested across import methods and OS versions.

## Manual pipeline

This example uses a JPEG Motion Photo. For HEIC input, adjust the intermediate still extension too.

```bash
SRC=/path/to/motion_photo.jpg
CID=$(uuidgen)

python3 tools/make_livephoto_still.py "$SRC" /tmp/source.jpg \
  --video-out /tmp/source.mp4 --uuid "$CID"

bin/mkstill /tmp/source.jpg IMG_LIVE.HEIC "$CID" heic --hdr preserve
bin/mkmov /tmp/source.mp4 IMG_LIVE.MOV "$CID"
bin/validate IMG_LIVE.HEIC IMG_LIVE.MOV
```

**The low-level splitter, still encoder, and video remuxer overwrite existing outputs. They do not
have the main entry point's `--force` protection.** Use separate output paths; never use your originals
as outputs.

By default, the video tool attempts to read the source video's date from `mvhd`, then uses it to
rewrite creation and modification times in the output's `mvhd/tkhd/mdhd` boxes. If the source date
is unavailable, the exporter's date is left unchanged. This process does not derive a date from
image EXIF or guarantee that the image and video originally had matching dates.

To override the video date:

```bash
bin/mkmov source.mp4 IMG_LIVE.MOV "$CID" \
  --date 2026-09-11T02:45:51Z
```

## Validation

### Read-only structural check

```bash
bin/validate IMG_LIVE.HEIC IMG_LIVE.MOV
```

The [validator](<tools/validate.swift>) decodes the still, loads video track information, checks that
the still and MOV identifiers match, and requires a `still-image-time` key in the MOV. A successful
check exits with code 0.

It reports HDR headroom / gain-map information but **does not use HDR fidelity as a pass criterion**.
It does not decode every video frame, validate timed metadata tracks or still-frame timing, or require
`live-photo.auto` to be present. Passing this check does not guarantee successful import into Photos.

### Actual Photos import test (modifies your photo library)

```bash
bin/pairtest IMG_LIVE.HEIC IMG_LIVE.MOV
```

The [pairing tester](<tools/pairtest.swift>) requests photo-library access and submits the image and
video to Photos as `.photo` and `.pairedVideo` resources. Check for `ACCEPTED` and `live=true` in the
output, then verify playback in Photos. The current exit code does not reliably distinguish authorization
failure or a rejected import.

This is **not a read-only test**. Remove test items from Photos manually afterward. If iCloud Photos
is enabled, the imported media may also sync. The one-command conversion does not run this test automatically.

## Known limitations and troubleshooting

- A regular still photo without appended video cannot be turned into a Live Photo by this tool.
- Proprietary layouts, malformed XMP, and large or unusual video containers may not be recognized.
  The scanner is not a general-purpose media repair tool.
- The splitter reads the entire input into memory. It is intended for short phone Motion Photos,
  not very large media files.
- If compiled tools are missing, run `bash build.sh`. Rebuild after source changes.
  The current entry point requires the validator binary even with `--no-validate`.
- If compilation fails because an API is unavailable, check macOS and the selected Xcode / Command
  Line Tools SDK. Changing HDR options cannot fix missing compile-time APIs.
- Passthrough may fail if the source video codec is unsupported by Apple platforms. In that case,
  transcode the video separately to a supported codec such as H.264 or HEVC. This tool does not
  automatically transcode video.
- Conversion does not sanitize private metadata. Stills may retain capture dates, GPS coordinates,
  and other source metadata. Inspect samples and outputs before publishing or sharing them.
- There is no automated regression test suite yet. Test representative files from your own devices
  before releasing results or migrating a large library.
